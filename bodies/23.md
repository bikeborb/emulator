### fix(common): merge the host mappings of driver-backed guest memory

With guest memory on the dma_bufs the GPU driver exports (Turnip on the
AYN Thor) the kernel does not merge neighbouring mappings of the
backing: remap_pfn_range gives every mmap its own VMA, flagged
VM_PFNMAP | VM_IO (smaps VmFlags "pf io"). memfd mappings merge, so this
never showed before. Nearly every guest map is one 4 KiB page and
almost nothing is unmapped, so a game ran into vm.max_map_count (65530
on the Thor, not changeable without root): "mmap failed: error=12" and
then the "Host VMA budget exhausted" SIGTRAP in MapPhysicalMemory on
New Game.

HostMemory merges them itself, only when the backing came from the
caller (merge_by_hand). Impl::MergeMappings reads /proc/self/maps
(ParseHostMapping), keeps the mappings inside the fastmem range that
belong to a backing chunk (fstat device and inode) and remaps every run
that ContinuesMapping accepts (same file, adjacent in memory and in the
file, same permissions and sharing) with one mmap(MAP_SHARED |
MAP_FIXED). It runs from the VMA sampler thread at a threshold (half
the budget, then max(half, left + budget / 8)) and synchronously on
ENOMEM in Map, Unmap and Protect, which retry once; Protect also asks
for a sample. Map, Unmap and Protect hold layout_mutex shared around
their syscalls, MergeMappings holds it exclusive.

On the Thor a probe over 60000 mappings reads them in 37 ms and remaps
them in 44 ms, with the data intact and read-only pages still read-only.
In a game a pass takes 23 to 423 ms and merges away up to two thirds of
the mappings; New Game goes through.

Tests: static_asserts for ContinuesMapping and a Catch case for
ParseHostMapping. The test arena shrinks from 2^39 to 2^38 bytes: a 2^39
reservation never fits on arm64 Android, and every HostMemory test
failed with bad_alloc on the device. All 21 pass on the Thor.

### fix(kernel): maintain the host instruction cache for guest code run in place

On the AYN Thor CTR_EL0 reads DIC = 0, IDC = 1, L1Ip = PIPT: the
instruction cache must be invalidated after code is written, and
ArmNce::ClearInstructionCache and InvalidateCacheRange only issue a
fence. Linux does the invalidation itself when it maps an executable
page, but only for ordinary page table entries (arm64 set_pte_at), and
guest memory on a dma_buf backing is mapped with special entries
(remap_pfn_range). With that backing nothing maintained the cache:
BioShock Infinite died with SIGILL at a guest pc inside the dma_buf
mapping about 60 s after boot.

Even on the memfd backing the initial module code got nothing:
KPageTableBase's InvalidateInstructionCache only reaches processes in
the kernel's process list, and Service::Process::Initialize adds the
process after the loader has returned. The NCE patch segment never
becomes executable in the guest page table at all.

Core::Memory::SyncInstructionCache(vaddr, size) goes page by page
through the backing pointer in the page table (always mapped
read-write; with a PIPT cache any alias reaches the lines; unmapped
pages are skipped, because UnmapCodeMemory asks after unmapping) and
calls __builtin___clear_cache, which does the dc cvau / ic ivau
sequence CTR_EL0 asks for. The kernel's InvalidateInstructionCache
calls it for each matching process before the per-core interfaces
(which drop recompiled code and stay for dynarmic), and
KProcess::LoadModule calls it over the whole module image once the
permissions are set. The body is under HAS_NCE: without NCE guest code
is recompiled, not run in place.

### fix(nce): report unhandled accesses and run data aborts through Core::Memory

An access NCE could not service was skipped silently: a data abort
advanced pc by four and went on, and one instruction shape (CBZ x0
right before ldr w8, [x0, #8]) was rewritten to take the wrapper's
null path instead. Both hide the first bad access and leave the log
pointing at whatever fails later because of it. The prefetch abort
path logged the registers but no call stack.

A data abort now does what dynarmic does for the same access: the
one-instruction interpreter already used for alignment faults runs it
through Core::Memory, where an unmapped read returns 0 and an unmapped
write is dropped. Only an instruction it cannot decode is still
skipped. The CBZ rewrite is gone.

Every unhandled access is reported with LOG_CRITICAL: kind, pc, fault
address, instruction word, what was done about it, core, thread, sp,
lr, pstate, the registers and the guest backtrace
(GetBacktraceFromContext). Data abort reports are capped at 16 per core
(m_reported_data_aborts) so a loop cannot flood the log.

### fix(host1x): give syncpoint waiters handles that survive other waiters

SyncpointManager keeps the registered actions in a std::vector (581b826
replaced the std::list) but still handed out iterators as the handle a
waiter later passes to DeregisterAction. A vector iterator does not
survive the insertions and erasures of other waiters, so a cancelled
timed wait (nvhost_ctrl ClearEventWait after a timeout) could erase
another waiter's action, a lost wakeup, or leave its own to fire later
on a stale entry.

ActionHandle is a u64 id now; 0 means the action already ran because
the value was reached at registration. RegisterAction takes the id
under the guard and inserts with std::ranges::upper_bound on
expected_value, so actions still run in order, and DeregisterAction
finds the action by id.

Tests in src/tests/video_core/syncpoint_manager.cpp: cancelling one
waiter keeps the others, actions run in order and once, a reached
value runs the action at once. A copy of the old logic fails the first
two.

### fix(nvnflinger): do not fail a dequeue over Android's async buffer rule

BufferQueueProducer::WaitForFreeSlotThenRelock kept Android's check
that returns BadValue when the dequeue is async and the override buffer
count is below the max. Before 66f5870 it could not fire, because
GetMaxBufferCountLocked returned the override as it was. Since then
queued and dequeued slots above the override raise the max, so a
SetBufferCount from 3 to 2 while slot 2 was still queued made every
async dequeue fail until the slot drained.

NVN dequeues with async set and takes a failed dequeue as a failed
acquire. It presents anyway with an acquired index of -1, whose texture
entry overlaps the window's NvRmSync pointer, so the next acquire waits
on a corrupted sync and the render thread stops. BioShock Infinite
froze on its loading screen with the music playing, and on New Game.

HOS has no async buffer mode (use_async_buffer is never set), so the
check goes; the slot-preserving max of 66f5870 stays. The game switches
between 3 and 2 buffers repeatedly and gets through the title, the menu
and New Game into the first level.
